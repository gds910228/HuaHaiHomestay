## 二、核心业务领域

1. **攻略内容(food/route/spot/info 四类)** —— 统一存 `guides` 集合,`category` 字段区分。列表/详情/收藏/浏览量。
2. **民宿与房型** —— `hostel`(单条) + `rooms`(多条),房型价格 `fixedPrice` 或 `price{low,high}`。
3. **实用信息仪表盘(info 页)** —— 天气 + 活动评分 + 潮汐曲线 + 渡轮 + 应急 POI 聚合,24h 本地缓存。
4. **管理后台(admin/*)** —— 密码登录后 CRUD 攻略/民宿/房型,富文本 + 图片列表。
5. **数据同步与维护** —— spot-sync(景点天气/步行时间)、route-plan(路径规划)、info-board(潮汐预热)、孤儿文件清理。

## 三、架构关键点(写 Rules 的依据)

- **云函数统一 BFF 模式**:5 个云函数全部单入口 `event.type` switch 路由,无一功能单文件。`huahai` 是面向前端的主 BFF(26 个 type),其余 4 个是运维/数据同步类,各自带 `lib/` 子模块。
- **内容模型归一**:`guides` 集合承载 food/route/spot/info 四类,靠 `category` 区分,非一物一集合。`geoLocation` 为 `db.Geo.Point` 且建地理索引(景点附近查询用)。
- **状态分层极简**:`app.js globalData` 只有云环境 ID,无业务全局状态;状态全在页面级 `data` + 云函数侧。
- **设计系统有真源**:`design-system/MASTER.md` 为唯一真源,token 落地 `miniprogram/app.wxss`;5 个组件全为展示型(卡片/图片/空态/加载态/骨架),无业务型组件。
- **定时触发器落地不一致**:仅 `spot-sync/config.json` 写了 triggers(每 4h 天气 / 每天 6 点全量);`info-board` 代码处理了 `event.Type==='Timer'` 且注释说"每天 0:30 触发",但 config.json 无 triggers —— **潜在漂移点,可能触发器在云控制台手动配,未落仓库**。

## 五、当前 AI 编码痛点(基线,供后续对比)

- **CLAUDE.md 严重过时**:仍描述"模板代码库 / 只有 quickstartFunctions demo / 未配 tabBar",与实际(16 页面 / 5 云函数 / 3 tab)脱节,AI 据此会给出错误指引。→ 待用本报告 + Rules 校正。
- **隐性知识散落**:12 条隐性知识此前只在 memory 和零散注释里,无集中 Rules,AI 每次重新踩坑(如又用 getLocation 被拒、又往代码里写密码)。
- **triggers 漂移未治**:info-board 的定时任务依赖未明,AI 改潮汐逻辑时可能不知道触发器实际在哪。
- **无变更管理**:54 次提交无标准化变更目录,需求-代码-评审不可追溯(SOP 阶段九要解决)。
- **无统一门禁**:无 CI、无强制 review、无 verification-before-completion 机制,AI 易"提前宣布完成"(Premature Victory)。
