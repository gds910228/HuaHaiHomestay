# 开发流程规范

> 常驻上下文(L1)。接需求到交付的标准流程。十阶段流程的精简版,完整版由 Application Owner Agent 调度(阶段五编写)。

## 一、需求到交付(精简十阶段)

| # | 阶段 | 主要动作 | 产出 |
|---|---|---|---|
| 1 | 需求分析 | 用 brainstorming skill 苏格拉底式澄清,产出 spec | `changes/<变更>/request_analysis/spec.md` |
| 2 | 需求评审 | 检查 spec 是否触碰审核合规/类目权限(见编码规范§9、§3) | `spec_review_v1.md` |
| 3 | 编码实现 | 用 writing-plans → executing-plans;改云函数先读工程结构§4 | `coding_report_v1.md` |
| 4 | 编码评审 | 用 requesting-code-review;查硬性约束清单 | `code_review_v1.md` |
| 5 | 单元测试 | 纯函数(utils/)必写测,放 `tests/`;云函数难单测则写调用脚本 | `test_report.md` |
| 6 | 测试评审 | 检查覆盖率与反模式 | `review/` |
| 7 | 代码推送 | 分支 + commit | — |
| 8 | 验证 | 用 verification-before-completion:**evidence before assertions**,贴真机/模拟器截图 | `verify_report.md` |
| 9 | 部署验证 | 云函数部署 + 触发器确认 + 真机走查 | `deploy_report.md` |
| 10 | 用户确认 | HITL 最终确认 | `summary.md` 收尾 |

【教训】AI 最常见的失败是「提前宣布完成」(Premature Victory)—— 阶段 8 必须跑验证命令/截图,不靠断言。

## 二、分支策略

- 默认分支 `main`,**不直接在 main 上写业务**
- 新需求开分支:`feat/<短描述>` 或 `fix/<短描述>`(如 `feat/tide-source`、`fix/fuzzy-location`)
- 提交信息前缀:`feat:` / `fix:` / `refactor:` / `docs:` / `chore:`,参考现有 git log 风格
- commit message 末尾由 Claude 协作的,加 `Co-Authored-By: Claude` 行

## 三、云函数部署流程

1. 本地改完 `cloudfunctions/<name>/`,确认 `config.json` 权限与 triggers 已更新
2. 部署:微信开发者工具右键云函数目录 →「上传并部署 - 云端安装依赖」
   - 或命令行:`uploadCloudFunction.sh`(模板脚本,按需改)
3. 部署后**必须验证**:云端日志看启动无错、前端调一次该 event.type
4. 涉及定时触发器:部署后在云控制台确认 triggers 生效(因 config.json triggers 是否自动同步取决于工具版本)

【教训】info-board 触发器漂移就是因为部署后没确认 —— 部署 ≠ 生效,要回查。

## 四、数据库变更流程

- 新集合:云控制台手动建 + 代码内 `ensureCollection` 兜底 + 更新 `docs/bak/DATABASE.md`(本地)
- 新字段:先在 `init-database` 加 seed/迁移逻辑,再让前端读;**不**假设旧数据有新字段(用 `??` 兼容)
- 权限:guides/hostel/rooms「所有用户可读、管理员可写」;favorites「仅创建者可读写」;新集合默认收紧
【教训】价格字段演进时旧数据无 fixedPrice,读取必须兼容 —— 任何 schema 变更都要考虑存量数据。

## 五、审核合规检查(上线前必过)

- 文案扫描:无"游玩路线/旅行社/预订/下单/支付"等敏感词(见编码规范§9)
- 权限最小化:只声明实际用到的 scope,模糊定位优先
- 类目自检:新增功能前确认当前类目(工具/天气/资讯)是否允许该 API
【教训】route 改名"南澳玩法"才过审 —— 合规检查前置到需求评审(阶段 2),不要等被打回。

## 六、Human-in-the-Loop 确认点(5 个)

需求待决议、计划评审后、编码评审后、部署参数、最终交付 —— 这 5 个点必须暂停等用户确认,不自动往下冲。

## 七、变更目录(每个需求必建)

`.harness/changes/{feat|fix}-{名称}-{YYYYMMDD}/` 下按 SOP 阶段九建子目录,`summary.md` 是全流程追溯的唯一真源,每阶段完成立即更新。

## 八、每发现一个错误

立即 Patch 到 Rules/Skills(如新踩一个审核坑,就补进编码规范§9)—— 工程化消除它再次发生的可能。
